# Open Source Markdown Style System

采用混合型开源 Markdown 风格：吸收工程基础设施项目的严谨、开发者产品项目的入口友好、社区协作项目的流程边界。目标不是模仿某个项目的表面风格，而是形成可信、易读、可执行的开源协作体验。

## 读者任务路径

1. 说明这是什么、给谁用、解决什么问题
2. 给出最快且安全的下一步
3. 区分常见任务、深入说明、参考资料和治理规则
4. 明确决策、约束、取舍和后果
5. 把贡献者引导到正确流程

## 文档类型指导

| 文档类型 | 读者问题 | 推荐结构 |
| -------- | -------- | -------- |
| README | 这是什么，为什么用，如何开始？ | 定位、快速开始、文档入口、示例、贡献、许可证 |
| RFC | 这个变更是否应该发生？ | 背景、动机、约束、方案、替代方案、缺点、生命周期 |
| ADR | 做了什么决定，为什么？ | 状态、背景、决策、后果、替代/废弃关系 |
| Guide | 如何完成一个任务？ | 前置条件、步骤、验证、排错 |
| AGENTS.md | Agent 在这里该如何工作？ | 仓库定位、约束、命令、所有权、升级边界 |
| Contributing/process docs | 如何安全参与？ | 工作流、标准、审查预期、沟通路径 |

## 推荐章节顺序

这些顺序是设计基线，不替代下游 Skill 的内容合同。当对应下游 Skill 存在时，以其模板字段为准。

| 文档类型 | 推荐章节顺序 |
| -------- | ------------ |
| README | 项目定位 → 适用读者 → Quick Start → 常见任务 → 文档入口 → 贡献 → 许可证 |
| RFC | 摘要 → 背景 → 目标/非目标 → 约束 → 方案 → 替代方案 → 缺点/风险 → 生命周期 |
| ADR | 状态 → 背景 → 决策 → 后果 → 替代方案 → 关联 ADR/RFC |
| Guide | 适用场景 → 前置条件 → 步骤 → 验证 → 排错 → 相关链接 |
| AGENTS.md | 仓库定位 → 核心原则 → 目录/所有权 → 常用命令 → 升级边界 → 禁止事项 |
| Contributing/process docs | 贡献范围 → 工作流 → 质量标准 → Review 预期 → 沟通与升级路径 |

## 不推荐结构

- 先讲内部目录，再解释项目用途
- 把教程、参考、治理规则混在同一长列表里
- 用“背景/说明/其他/补充”堆章节，却不告诉读者下一步
- README 一上来列完整架构，而没有 Quick Start 或文档入口
- RFC 只写方案，不写目标、非目标、替代方案、缺点或生命周期
- ADR 写成复盘文章，而不是可追踪的决策记录
- Guide 缺少验证步骤，让读者不知道是否完成
- 流程文档只写原则，不写责任人、评审路径或升级条件

## 中文技术文档风格

- 短句优先；一句话只承载一个主要判断
- 先给结论，再给原因
- 术语稳定，同一概念不要在“能力/功能/模块/组件”之间摇摆
- 保留必要英文术语，如 `Skill`、`Agent`、`README`
- 少用“强大”“优雅”“丝滑”“极致”等抽象形容词
- 少用“被设计用于”“使得用户能够”等翻译腔
- 中英文混排保持空格，但不要为了形式破坏术语可读性

## 写作与审查规则

- 先给读者价值，再给实现细节
- 标题使用任务导向表达，避免“说明”“其他”“补充”
- 链接要成为行动路径，不堆参考资料
- 流程性文档写清生命周期、所有者和评审边界
- 只审查结构和阅读路径；只有下游 Skill 明确要求时，才把字段缺失列为 finding
- 改写时只在源文已暗示时补充骨架；事实不足时使用 `TODO:`
- 保持短文档短，不把轻量说明扩成治理文档
